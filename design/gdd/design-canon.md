# 《江湖一生》設計典律（Design Canon）
*唯一真相來源 | 2026-05-12 | 所有其他文件如有衝突以此為準*

---

## 一、設計原則（7條強制）

### 1. Severity 連續值模型
- **禁止**使用輕/中/重三段離散枚舉
- 所有狀態、成長、關係值使用 0.0→1.0 連續 severity
- 關鍵閾值（0.3 / 0.6 / 0.9）觸發 stage 效果
- stage 效果可以是：屬性修飾詞、行為限制、事件觸發、UI 變化

### 2. 修飾詞疊加架構
- **禁止** if-else 分支計算最終屬性
- 所有 buff/debuff 作為修飾詞疊加：`最終值 = (基礎 + Σ加法) × Π(1 + 乘法)`
- 疊加順序：aged衰減 → flat加法 → percentage乘法 → setMax上限
- 設計文件必須標明每個修飾詞的類型（臨時/條件/永久）

### 3. 資料驅動
- 所有遊戲平衡數值外部化到 `assets/data/` 的 JSON/Resource 檔
- 設計文件的「可調參數」章節必須列出每個值和安全範圍
- 策劃改數值不需要程序員介入

### 4. 對稱 Trade-off 設計
- 每個特質/技能/選擇必須有明確的正面**和**負面效果
- **禁止**純優點設計
- 格式：「攻擊+8，魅力-300（天煞孤星）」

### 5. 事件鏈而非單一事件
- 重要事件設計為「觸發 → 選項 → 後果 → 後續事件」的鏈條
- NPC 反應作為獨立事件設計，不硬編碼進主事件

### 6. 情境先行設計方法
- 任何新系統設計必須經過三階段：
  1. **發散**：列出 15-20 個玩家真實遭遇的具體情境
  2. **收斂**：從情境推導出最小機制屬性集合
  3. **再發散**：用邊界情境驗證規格覆蓋度
- **禁止**直接從「系統應該有哪些功能」出發設計

### 7. 系統邊界紀律
- 每個 GDD 只描述**本系統自己的行為**
- 「其他系統收到事件後如何反應」屬於對應系統的 GDD，不是本系統
- 本系統只廣播事件，不定義接收方的行為

## 二、沙盒設計原則

- 玩家出生時與任何 NPC 的關係不存在
- NPC 關係在**第一次實際遭遇**時建立，那一刻同時套用出身修正 + 性格修正 + 名聲修正
- 不存在「初始化所有 NPC 關係」的操作

## 三、武俠語言規範

| 禁用（修仙詞彙） | 正確（武俠詞彙） |
|---------------|--------------|
| 靈力、法力 | 內力 |
| 靈根、資質（修仙語境）| 武學資質、天賦 |
| 修煉（境界突破）| 練武、武功精進 |
| 丹藥（修仙）| 藥材、金瘡藥、補血藥 |
| 法寶 | 兵器、暗器、神兵 |
| 宗門 | 門派、幫會 |

## 四、GDD 品質標準

### 8 個必要章節（缺一不可）

1. **概述** — 一段話說明系統是什麼、做什麼
2. **玩家體驗** — 玩家使用此系統時的感受目標（MDA 情感語言）
3. **詳細規則** — 無歧義的完整機制，每條規則可以直接實作
4. **公式** — 所有數學計算：變數定義、公式、範例計算、取整規則
5. **邊界條件** — 每個特殊情況的具體處理（禁止寫「合理處理」）
6. **系統依賴** — 依賴哪些系統、哪些系統依賴它（**雙向必填**）
7. **可調參數** — 每個可調值的預設值和安全範圍
8. **驗收標準** — QA 可逐條測試、有明確預期結果的測試案例

### 草稿品質自查清單（每份 GDD 提交前必過）

- [ ] 有 severity 連續值嗎？（狀態類系統必須有）
- [ ] 屬性計算用修飾詞疊加嗎？（不是 if-else）
- [ ] 數值都是具體的（百分比、數字），不是「顯著影響」這類模糊描述？
- [ ] 每個功能都有 MVP / V2 邊界標示？
- [ ] 有公式 + 範例計算（含邊界值）？
- [ ] 有驗收標準（QA 可逐條測試）？
- [ ] 系統依賴雙向填寫了嗎？
- [ ] 全程武俠語言？
- [ ] UI 顯示的值都是整數嗎（無小數）？
